# app-ai — Prompt-Grouped Inference (Cloudflare Worker)

**Parent:** [LimeSpot/CLAUDE.md](../CLAUDE.md)

The seven always-in-context hard rules bind here and are inlined for Codex in [AGENTS.md](AGENTS.md) beside this file. The depth behind them lives once in the workspace repository's `../_standards/*.md` — `engineering`, `testing`, `documentation-and-comments`, `git-and-approval`, `architecture`, `naming`, `security`, `web-ui` — read on demand. This file carries only what is specific to app-ai and never restates a workspace standard. Activate this repository's git hooks once per clone: `../_enforcement/install-git-hooks.sh app-ai`.

A Cloudflare Worker that validates merchant context and runs a provider-neutral inference service. Production prompt groups route to Anthropic except the protected-CI visual judge, which runs on the configured Cloudflare Workers AI vision model inside the daily free allocation. OpenAI Responses and Gemini `generateContent` remain dormant candidates pending recorded prompt-level evaluation; Moonshot/Kimi Chat Completions (the metered platform account and Kimi Code subscription account) may serve only routes that carry no customer content, and no route is such a route today ([docs/AI-PROVIDERS.md](docs/AI-PROVIDERS.md)). It holds the provider API keys, validates ordinary merchant requests through Personalizer, and provides a separate origin-scoped extension audit exchange for stores without a LimeSpot Context-ID. It serves **production**: every Studio AI surface reaches `/files`, `/messages` and `/chat`, the App's subscription chat reaches `/chat`, and the scoped extension audit sessions reach `/files` and `/messages`.

The protected visual judge requires Brain's `AdministerAllSubscribers` proof, an enabled deployment
switch, a route pinned to the exact Cloudflare Workers AI model `@cf/qwen/qwen3.8-27b`, and an atomic UTC-day
reservation from a separately addressed `AuditSessionAuthority` instance after request validation
and immediately before the Workers AI binding is called. Focused diagnostics stop before the
configured acceptance reserve. The handler places the protected header in typed request authority;
caller metadata never selects a quota class. The internal reservation contract is documented in
[src/lib/CLAUDE.md](src/lib/CLAUDE.md). Reusing the deployed authority class keeps preview uploads
migration-free. Brain's authorization proof must deploy before this worker, and this worker must
pass its authenticated route smoke before lib points protected CI at it. A lib build without the
quota-class header is diagnostic and can use only the daily limit minus the reserve. Because that
header requires this worker's CORS allowlist, rollback removes the lib sender before this worker.
Production `/health` validates the protected route's binding, authority, internal origin, enable
switch, daily limit, and acceptance reserve before reporting the deployment ready.

## Definition of Done (ENFORCED)

Work in this repo is DONE only when **all** of the following hold — anything
less is not done, and must not be reported as done:

1. **Scope = all of it.** 100% of the agreed scope ships. No deferrals, no
   "later phase", no "good enough", no silently narrowed scope. If a piece
   genuinely cannot land (e.g. it requires a Brain-side change), that is
   surfaced explicitly as a blocker with a written handoff — never quietly
   dropped.
2. **Full test coverage on all of it.** Every new behavior is covered at every
   applicable layer: unit/integration → contract (frozen shapes/snapshots) →
   architecture fitness scans — and, before a release, the live token-savings
   gate (docs/TESTING.md).
3. **All tests passing.** The FULL suite, as CI runs it on the pushed head — not just the new
   tests. A red test anywhere means not done.
4. **No preexisting bugs accepted.** A bug surfaced along the way gets fixed —
   "it was already broken" is not an exemption. If the fix is genuinely
   out-of-repo (Brain, lib), it gets a root-cause writeup, and the failing
   test stays honest (never weakened, never skipped to green — see
   docs/CODE-PATTERNS.md → No Silent Skips).
5. **All gates green, with zero errors:** CI's five jobs — `npx vitest run` with
   root's published-DPA checker beside it, `npm run lint`, `npm run format-check`,
   `npm run typecheck`, `npm run deploy:dry-run` — green on the pushed head, and the documentation
   tree updated with the change (this file's propagation rule).
   Locally, a push is preceded only by the format check, lint and typecheck; a test runs locally
   only for an exception `../_standards/testing.md` → Local gates names (a reported bug's
   reproduction, UI visual evidence, a suite CI does not run, a red exact-head CI test, a vacuity
   probe).

Verification is independent: gate results are read from the exact-head CI run, not taken
from a summary. Reporting "done" with any of the above unmet is the failure
mode this section exists to prevent.

## Key Principles

See [docs/CODE-PATTERNS.md](docs/CODE-PATTERNS.md) for the detailed standards. Summary:

- **DRY** — shared logic lives in `lib/`; one implementation per concern.
- **Single Responsibility** — one module = one concern; the router routes, handlers build canonical requests, `src/inference/` owns runtime/provider translation, and `src/config.ts` is the only binding reader.
- **No Dead Code** — unused exports, commented-out blocks, and "just in case" shims are deleted, not kept.
- **No Hardcoded Config Values** — URLs + deploy-time tunables in config, read through `src/config.ts`; missing config throws; no inline fallbacks (Tech / Constraints above).
- **One Error Shape** — every error is the Brain wire envelope via `lib/responses.ts` (Hard rules below).
- **Brain Is the Single Source of Truth** — anything crossing the Personalizer API boundary mirrors Brain's C# exactly; verify in the sibling `brain` repo, never the sibling `app` TS, which can be stale (Hard rules below).
- **Secrets stay server-side** — API keys, bearer tokens, cookies, passwords, service credentials, and request context-IDs are never model-visible or logged. Request/subscriber IDs provide operational correlation (docs/TOOLSETS.md; fitness-tested).
- **No Silent Skips** — tests never skip on a missing precondition; they throw with an actionable error.
- **Current-state docs** — the documentation tree describes what IS (Documentation conventions above) and updates in the same commit as the code.

The review prompts use four explicit correction verbs. `styleBox` changes appearance, `removeBox`
removes, `addBox` creates a missing box, and `moveBox` relocates an existing box. Relocation is never
encoded as remove+add; lib rejects both halves of that ambiguous pair atomically. The shared prompt
contract and synchronization points are documented in [src/prompts/CLAUDE.md](src/prompts/CLAUDE.md).

## Tech / Constraints

- **Strict TypeScript (ES modules).** `tsconfig.json` declares the full strict family plus the beyond-strict correctness flags (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, …). No `any`, no `@ts-ignore`/`@ts-expect-error` — `unknown` + narrowing instead (docs/CODE-PATTERNS.md → Strict TypeScript). `npm run typecheck` (`tsc --noEmit`) is a required gate; there is no separate build step — wrangler/esbuild transpiles the TS natively at deploy time, vitest/vite at test time.
- Cloudflare Workers runtime (V8 isolates, Web-standard `fetch`/`Request`/`Response`/`FormData`) — **no Node.js, no runtime filesystem.**
- No production npm dependencies (nothing is bundled into the deployed worker). Dev-only: `wrangler`, `vitest`, `typescript`, `typescript-eslint`, `eslint`, `prettier`, and — for the free local Claude-Code testing channel (`scripts/dev-claude-shim.mjs` and its record/replay cache `scripts/dev-shim-cache.mjs`) — `@anthropic-ai/claude-agent-sdk` + `zod`. The shim is standalone Node tooling run by `npm run dev:shim`; it is never imported by `src/` and never ships to production.
- **No Hardcoded Config Values (ENFORCED).** Every URL and deploy-time tunable (Personalizer/provider origins, credentialed CORS origins, model choices, the master subscriber) lives in configuration — wrangler.toml `[vars]` (production) / `.dev.vars` + committed `.dev.vars.example` (local) — and is read ONLY through the typed accessors in `src/config.ts` (the single typed `Env` interface). **Missing config = a thrown error naming the variable and where to set it. No fallback defaults anywhere** — `env.X || …` / `env.X ?? …` is banned. True contract constants (wire field names, tool names, routes, prompt text, Anthropic's 4-breakpoint limit, the contract-frozen `MAX_ITERATIONS` / `MAX_CHAT_REFS`) stay in code — as does the model catalog, which records what a model IS rather than which one a deployment chose. Full rule: docs/CODE-PATTERNS.md → "No Hardcoded Config Values"; enforced by the fitness scans in `test/architecture.test.ts` and the production-value pins and Env/`.dev.vars.example` reconciliation in `test/config.test.ts`.
- **Provider API keys never leave the worker.** Only each provider's wire adapter reads its key through `src/config.ts` (`anthropic-wire.ts`/`claudeApiKey`; `openai-wire.ts`/`openaiApiKey`; `moonshot-wire.ts`/`moonshotApiKey`; `kimi-wire.ts`/`kimiApiKey`; `gemini-wire.ts`/`geminiApiKey`).
- **The Personalizer integration-bridge token (`PERSONALIZER_INTEGRATION_BRIDGE_TOKEN`, Workers Secret) never leaves the worker.** Only the platform toolsets' call-channel seam (`src/toolsets/integration-bridge.ts`) reads it, via `personalizerIntegrationBridgeToken(env)` from `src/config.ts`; it is sent solely as the `X-Personalizer-Integration-Bridge-Token` header toward Personalizer's integration bridge — never a `wrangler.toml` var, never logged, never model-visible.
- **Audit signing keys are separated.** The website shares `AUDIT_ACTIVATION_SIGNING_SECRET` for activation assertions and the distinct `AUDIT_STATUS_SIGNING_SECRET` for app-ai callbacks; `AUDIT_SESSION_SIGNING_SECRET` remains app-ai-only. All three are encrypted secrets with at least 32 bytes and never model-visible.
- **`TOKEN_ENCRYPTION_SECRET` is a required Workers Secret.** It is 32 random bytes encoded as base64 and is an HKDF ROOT, not a cipher key used directly: separate AES-GCM and HMAC subkeys are derived from it for sealed opaque file references, sealed inference continuations, and the keyed tenant pseudonym that scopes both. Its name states that role rather than any one token type, because no part of it is file-specific. Never log or place it in `wrangler.toml`; rotating it invalidates outstanding file references (bounded to at most 15 days) and continuations (at most 24 hours).
- Deploy is automatic from `main` via Cloudflare's GitHub integration — **pushing `main` deploys to production**, which is why `main` is read-only to every agent and that push is an operator step carrying its own deploy approval (Hard rules below).

## Architecture

Entry/router → handlers → the canonical inference service → the selected provider adapter, over shared lib + toolsets. The router is thin; handlers never construct provider payloads. Five chokepoints hold the split together: `src/config.ts` is the ONE place a binding is read, `src/inference/model-catalog.ts` the ONE place a model id implies a provider, `src/inference/factory.ts` the ONE place an adapter is selected, `src/lib/responses.ts` the ONE error shape, and `src/prompts/` the ONE location prompt text lives in. Which module owns what is the folder-by-folder map in [docs/ARCHITECTURE-MAP.md](docs/ARCHITECTURE-MAP.md), read on demand; each folder's own rules are in its `CLAUDE.md`.

`src/lib/ai-providers.ts` is the ONE list of AI providers the worker may use. In production the router validates every route's provider and every provider API base against it before an isolate serves its first request, route resolution refuses a disallowed provider again before any credential is read, and every provider transport call goes through the non-following `fetchProvider` ([docs/AI-PROVIDERS.md](docs/AI-PROVIDERS.md)).

The `chat` prompt is LimeSpot Assistant, the store's eCommerce manager leading its agent team.
lib sends the team's state, and in an agent's own chat that agent's latest result, as
`context.grounding.growthAgents` data, and a Support request, a new agent run or a guided path is a
directive lib carries out; in a conductor's own chat it answers as that conductor from the open
step's plan, and a box move is the `moveBox` directive; app-ai calls no agent route
([docs/prompts/chat.md](docs/prompts/chat.md)). `requestSupport` and `moveBox` are taught only to
a client whose `/chat` request lists them in `clientActions`, so a lib build or a conversation
without their handlers is never asked to open Support or move a box (`src/lib/client-actions.ts`).

Studio chat counts toward the store's monthly AI cap together with its agent runs. After the reply,
`lib/brain-usage.ts` reports each completed provider response under a merchant Context-ID, its
model and token counts, to Brain's `POST v2/agents/report-chat-usage` through the request's
`waitUntil`, and Brain prices and stores it, marking use under a LimeSpot staff session as staff and
leaving it out of the cap. `billing-assistant` alone carries the registry's `excludedFromStoreAiCap`
and is not reported; an audit session has no store, and a response with no token counts, as the
protected visual judge's Workers AI answer is, sends nothing. app-ai sends tokens and the model,
never a cost, so Brain's `AI:ModelPricing` stays the one price list. A failed report is logged and
never retried, and no report changes or refuses an answer: a reached cap pauses agent runs in Brain
and chat keeps answering.

The Optimization conductor's four steps, `optimize-boxes`, `optimize-ads-audiences`,
`optimize-progress-bar` and `optimize-bundles`, are one-shot `/messages` prompts lib calls in a
fixed order with JSON data it built, beside the specialist agents it starts side by side. The box
step writes the words over the Merchandising Agent's box changes already in the draft; the others
choose among the options lib sent, by key, and write the words the owner reads, under the agents
master rules; lib writes every number and every draft change
([docs/prompts/optimize-boxes.md](docs/prompts/optimize-boxes.md#the-four-steps)).

The `billing-assistant` prompt is a no-tool `/chat` surface for subscription experiences. It
carries the agents master rules, answers only from the request's current pricing grounding, never
accepts payment secrets, and cannot mutate an account or subscription.

### Routes

`src/index.ts` IS the route table — it is the only router and short enough to read directly, so no copy of it lives in a document. The invariant it encodes: `/health` is the only unauthenticated route; `POST /audit/session/exchange` is authenticated by a website activation JWT and `GET /audit/session` by a scoped audit bearer alone; every other route requires a merchant context-ID, and only `POST /files` and `POST /messages` additionally accept a scoped audit bearer. A new route is added there and nowhere else.

`GET /prompts` is the one MASTER-gated route: after ordinary context-ID validation, `handlePrompts` requires the resolved `SubscriberID` to equal `MASTER_SUBSCRIBER_ID` and answers every other validated merchant with the router's unknown-route body byte for byte, so a merchant cannot confirm it exists. It reports each registered prompt's group, tier, resolved model/provider/API family/file policy, declared capability requirements, whether the resolved model honours inline cache breakpoints, and whether that route validates — plus the NAMES of required secrets still blank, never a value, prefix, or length. It is also the one route that reads its context-ID from either the `X-Personalizer-Context-ID` header or a `personalizerContextId` query parameter — the header wins when both are present, and the master gate is identical either way. The URL form is a master-operator convenience for opening the diagnostics in a browser, at the honest cost that browser history and any intermediary recording URLs sees the credential, so automation keeps to the header. `src/handlers/prompts.ts` owns the parameter name and is the only module that reads it; `src/lib/logger.ts` strips the value of a credential-bearing query parameter from every string entering a sink. Both are pinned by the fitness scans in `test/architecture.test.ts`.

Normal auth calls `validateContextId(X-Personalizer-Context-ID, env)` before dispatch, taking the credential from the header on every route and additionally from the `personalizerContextId` query parameter on `GET /prompts`. The alternate audit path exchanges an exact, email-verified website JWT once — a repeat exchange answers the same session until that session's first proposal reservation ([docs/AUDIT-AUTH.md](docs/AUDIT-AUTH.md#exchange-and-session-contract)) — and accepts only an app-ai-signed `ls_audit_…` bearer plus the extension's active-tab-origin header; the exchange and that header each name the signed store in its bare or its `www.` form, and no other origin (`lib/store-origin.ts`). A session lasts `AUDIT_SESSION_TTL_SECONDS` (30 days), the one value that bounds it — the bearer's expiry claim, the session record, an answered chat message's replay outcome and fingerprints, and how long the audit's record outlives its latest session — while every spending cap stays per run or per day. A session's uploads — the Anthropic files, Kimi's encrypted R2 evidence, and the session's `FILES_KV` dedup records and `discard:` keys — are deleted by the audit's alarm one reservation lease after the session expires or is superseded, every delete abandoned as failed after ten seconds and retried at growing intervals until it succeeds or the object's provider expiry passes, and the audit's whole record a session lifetime after its latest session expired ([docs/AUDIT-AUTH.md → Retention](docs/AUDIT-AUTH.md#retention)). A valid new activation for the same audit supersedes its active session: the old bearer answers `audit_session_expired` and the audit's progress carries into the new one. Two dated kill switches end cached runs: a session whose current run completed, or never completed and opened, before `GRADER_RUNS_VALID_FROM` is refused 410 `grader_run_revoked`, and an extension build naming an `X-LimeSpot-Extension-Built-At` before `GRADER_EXTENSION_BUILT_AFTER` is refused 409 `extension_update_required` at exchange and on every audit call — the cutoff applies only to a build naming its build time, and a build naming none is held to the plan version it names instead; the exchange and the read-only `GET /audit/session` status call report both as `runsValidFrom` and `extensionBuiltAfter`, and every chat reply as `graderChat.runsValidFrom`; the exchange resolves all of it before consuming the activation ([docs/AUDIT-AUTH.md → Kill switches](docs/AUDIT-AUTH.md#kill-switches)). A client names the grader plan it follows in `X-LimeSpot-Audit-Plan-Version`: a version the worker holds no allowance for is refused before any run starts, and a missing declaration follows plan 1 from a build naming its build time and is refused from one naming none, so a request naming neither header is refused. One check, `assertCompatibleAuditClient`, holds the exchange, `GET /audit/session`, `/files` and `/messages` to both rules. Audit scope is five onboarding upload destinations, the two onboarding proposal inference prompts, and — under plan version 2 — the `grader-chat` sales chat about the audit's own report (`handlers/grader-chat.ts`), each reserved before any paid work, plus the read-only, unreserved `GET /audit/session`; it cannot delete files, call `/chat`, use Brain, or choose model/tools/effort. A merchant context-ID naming `grader-chat` is answered as an unknown route. The chat keeps its own accounting beside the audit's — an audit allowance that neither a retry nor a reopened link restores, a hashed-visitor and a deployment UTC-day counter whose holds stay charged until explicitly committed or released, with a volume alert the deployment counter's alarm delivers from its own outbox, all three held under one reservation and settled idempotently with the audit's ledger first, each message idempotent by the caller's `messageId` so a replay returns its stored outcome with no inference or charge — the outcome, the identifier and the transcript and reply fingerprints deleted together 30 days after the answer — claims governed by a hardened boundaries prompt grounded in the booklet (the report is never an authority) beside an "AI can make mistakes" disclaimer lib shows, a reply withheld in code only when it carries a URL, links off limespot.com, or holds anything but plain text beside its one valid buttons block, since lib shows it as plain text, and history matched to the audit's own reply fingerprints — and never logs message text ([docs/AUDIT-AUTH.md → Grader chat](docs/AUDIT-AUTH.md#grader-chat)). Its audit-keyed Durable Object atomically serializes tile uploads and owned file IDs, divides a session into grader runs — a retry opens a fresh run, a new proposal request supersedes one its caller abandoned, and each run is held to one abuse ceiling derived from the grader plan (`lib/audit-plan.ts`) rather than a fixed count — limits the retries a session may start, enforces two completed public runs across reissued links — refusing the upload that would open a third before any provider call — and durably mirrors status to website D1 at the destination the activation signed — the required `statusCallbackUrl` claim, resolved once against the `AUDIT_STATUS_ORIGINS` allowlist and stored with the session, so the website owns its route while app-ai owns which hosts a callback may reach. Exact claims, public-origin vs verified `@limespot.com` entitlement, callback signing, limits, global-cap ownership, and deployment are in [docs/AUDIT-AUTH.md](docs/AUDIT-AUTH.md).

### Canonical inference runtime (`src/inference/`)

Both inference handlers build `InferenceRequest`/`AgentRequest` values and call the provider-neutral service. `model-catalog.ts` turns a configured model id into a provider, API family, capability set, and direct-file policy: versioned families match by prefix while provider-fixed Kimi/Moonshot service ids match exactly. Those are model facts in code while model IDS stay configuration; an id no family claims throws at resolution rather than defaulting to a provider. `service.ts` owns the multi-turn tool loop; `factory.ts` is the only adapter switch, and a provider the catalog can name but no adapter serves fails there, before provider I/O. Each adapter owns serialization, streaming, files, reasoning/structured output, usage/stops/errors, and continuation. Anthropic additionally owns prompt caching, token estimates, and the bounded raw `/messages` compatibility path, whose answer it holds to the registered token-count contract and whose canonical usage the factory's passthrough service hands the handler as `usage(body)`, so the passthrough is reported to Brain like any other response; OpenAI owns Responses Items/SSE with no stored Responses object (`store: false`; OpenAI still holds its automatic prompt-cache state, in memory for minutes or up to 24 hours of extended caching for an organization without Zero Data Retention, and app-ai requests no explicit cache), one-turn stateless requests (an OpenAI route offers no continuation and refuses an earlier assistant turn, tool result or caller tools, and no route whose conversation carries earlier turns or browser-owned tools can select it), output items, encrypted reasoning included, replayed only on the next server-tool iteration of the same request, and `user_data` Files API translation; Moonshot owns Kimi Chat Completions, sealed exact tool transcripts, strict `[DONE]` SSE, and direct image Files translation — one implementation serving both the metered platform account and the Kimi Code subscription account, which differ only by an account descriptor. The subscription side uses encrypted worker-managed evidence and native image uploads; text evidence is inlined when small, while oversized HTML is decrypted once per request and reduced through bounded internal retrieval. Gemini owns `generateContent`, its `x-goog-api-key` transport, sentinel-free SSE that completes on a clean close after a finish reason, the two-call resumable Files upload, mandatory `thoughtSignature` replay through sealed continuation state, the split of its single `maxOutputTokens` into the canonical answer budget plus a thinking allowance for the resolved `thinkingLevel`, and the stable-prefix emission order that earns its implicit cache. Cloudflare Workers AI owns the non-streaming, inline-image protected visual judge and fails closed when its binding, one required image, or response text is absent. A terminal Gemini turn with neither visible text nor a tool call is a normalized failure, never an empty success.

`src/inference/deadline.ts` is the ONE time limit on a model call: every upstream inference call — registered `/messages`, each `/chat` turn, and the unregistered passthrough — runs under `UPSTREAM_INFERENCE_DEADLINE_MILLISECONDS`, the provider's documented ten-minute limit for one request held open for a single answer, beside the caller's own cancellation. lib and the extension hold no deadline of their own and wait for app-ai's answer or error. The Anthropic adapter's `complete` streams upstream, as the provider advises for large output budgets, and assembles the exact non-streaming message body, so `/messages` still answers with one JSON message. Rationale and sources: [docs/DECISIONS.md → One upstream inference deadline, owned by app-ai](docs/DECISIONS.md#one-upstream-inference-deadline-owned-by-app-ai).

A `/messages` caller on a network that drops a request receiving no reply bytes for a while opts in with `"responseMode": "keep-alive"` in its JSON body. app-ai reads that field only after the caller has authenticated — a merchant's context-ID validated, or a Grader session's bearer verified and its body past the audit byte limit, the body read once, parsed once and handed to the handler as that one value (`lib/request-body.ts`) — and begins the keep-alive answer only once the request is authorized, so a refusal while authenticating or authorizing is answered with its own status and plain error body. It then removes the field (`lib/keep-alive-response.ts`), answers 200 with its headers at once, writes a whitespace byte immediately and every `MESSAGES_KEEP_ALIVE_INTERVAL_MILLISECONDS` while the request runs, and ends with one JSON envelope carrying the status the request would have answered with and either today's success body as `result` or today's Brain error envelope as `error`. Only that exact value opts in; every other request is answered exactly as before, so released clients keep today's statuses. The upstream deadline remains the only time limit, and a Grader chat replay reaches a keep-alive caller as the same stored outcome. Rationale: [docs/DECISIONS.md #36](docs/DECISIONS.md#36-a-long-messages-call-can-keep-its-connection-alive-by-the-callers-choice).

`src/inference/adapters/anthropic-wire.ts` is the single place that talks to the Anthropic API. It owns the base URL, `anthropic-version`, key injection, and the per-surface `anthropic-beta` flags — the `ANTHROPIC_VERSION` / `MESSAGES_BETA` constants at the top of that module are the source of truth for their values, and no document restates them. Files API calls send no beta flag: the Files API is generally available, and its beta flag hides each file's `expires_at`. Like every provider transport it calls `fetchProvider`, which follows no redirect.

No handler imports provider wire types or re-implements provider transport logic. The configured tier bindings resolve ordinary prompt groups to Anthropic; the protected visual alias alone resolves to the exact bounded Cloudflare Workers AI model `@cf/qwen/qwen3.8-27b`. The Kimi Code subscription accepts its four documented model IDs, with semantic effort on K3 and K2.8 and preserved thinking on K2.7 HighSpeed. Its stream may repeat identical terminal usage in a final empty-choices chunk; conflicting usage fails. Cached and reasoning token counts normalize from the provider's detailed usage fields when present. What a change of any binding must prove is [docs/MULTI-PROVIDER-DELIVERY.md](docs/MULTI-PROVIDER-DELIVERY.md).

### Token-saving levers (prompt caching, dedup, count_tokens, effort)

Cost-reduction is additive and never changes external request/response shapes.

**What caches, measured live (Opus 4.8 / Haiku 4.5):**

- **`/chat` + onboarding (Opus 4.8) cache.** The cached prefix is `tools` (TOOL_DEFINITIONS, ~6.4KB JSON) + the `buildSystem` base prompt block, ~1351 input tokens. A repeat call reads the full ~1351 from cache (`cache_read_input_tokens: 1351`, `input_tokens: 89`). The effective Opus-4.8 cacheable prefix is therefore ≤1351 tokens — the TOOL_DEFINITIONS block is what clears the floor (a tool-less prompt this small would not cache). The agent-loop conversation breakpoints (below) extend this to the growing turns.
- **Placement file blocks (Haiku 4.5) cache — the big win.** The placement flow uploads a screenshot + cleaned HTML via prompt-aware `POST /files`, then sends the returned opaque references as `fileIds` in `POST /chat`. Those file blocks (thousands of tokens — they dwarf the ~370-token placement system prompt) carry a 1h breakpoint on the LAST block, so a repeat placement call on the same page reads them at 0.1× (`cache_read_input_tokens` > 0 on call 2). Route-scoped dedup keeps the hidden upstream object stable, so the bytes hit the same cache entry.
- **Placement _system_ prompt (~370 tokens) does NOT cache and is left uncached — by design.** It is well under Haiku 4.5's minimum cacheable prefix; a `cache_control` marker on it would be a silent no-op, and padding it to clear the floor would cost more than it saves. The placement win is the file blocks, not the system prompt. (`buildSystem` still attaches the 1h marker to the base block because chat/onboarding share that path and DO clear the floor via tools; on placement the marker is harmless — the API ignores an unmet prefix — but it is genuinely inert there.)

**The levers:**

- **Extended 1h prompt cache.** Handlers assign provider-neutral `CacheIntent`s; `inference/cache.ts` keeps the canonical request within the four-slot Anthropic parity budget, and `adapters/anthropic.ts` realizes those intents as `cache_control`. The bounded unregistered-selector raw `/messages` passthrough uses the wire allocator in `adapters/anthropic-cache.ts`.
- **Agent-loop breakpoints.** `DefaultInferenceService.runAgent` reapplies canonical short-lived conversation breakpoints each iteration (last block + ~15-block intermediates), reserving the stable prompt/file prefix budget.
- **Implicit prefix caching on a provider without breakpoints.** `inlineCacheBreakpoints` says whether a provider honours per-block cache markers; the Gemini and OpenAI families do not, and each caches a repeated request PREFIX automatically instead. No prompt group requires the capability — honouring markers is a cost characteristic, not a correctness one — so `adapters/gemini.ts` honours a canonical cache intent by ORDER: every component that repeats for a prompt is emitted before `contents`, canonical block order inside `contents` is preserved so reusable evidence leads and per-call content trails, and nothing in that prefix varies per request. `GET /prompts` reports the flag per prompt so an operator sees which prompts' markers are inert.
- **Prompt-aware direct files (`files.ts` + `inference/file-references.ts`).** No `/files` verb assumes a provider, and none reaches an object its caller did not create: `DELETE /files/{id}` reads the route out of the sealed reference it is handed and refuses one minted for another tenant or for a route since configured onto another provider, and nothing enumerates a provider account — one account holds every tenant's uploads, so `GET /files` is not a route and falls through to the router's 404 `RecordNotFoundException`. Every upload declares one or more registered prompts. After multipart parsing, app-ai validates every destination, sealing-key configuration, and prompt → group → profile/provider/account/file policy route before provider I/O, collapses same-route destinations — including groups that borrow another group's file route, so a cascade's evidence is uploaded once — uploads distinct routes concurrently, and returns authenticated encrypted opaque tokens bound to a keyed tenant pseudonym. Route metadata is self-contained ciphertext under `TOKEN_ENCRYPTION_SECRET`, so immediate inference never depends on eventual KV propagation. Provider-managed file bytes go directly to providers; Kimi evidence is stored encrypted in INLINE_EVIDENCE_R2 until expiry or deletion. Missing/unknown prompts, malformed/expired/tampered tokens, missing/malformed sealing config, and tenant/account/policy/group mismatches fail before provider I/O. Registered/canonical inference rejects raw provider IDs; the bounded absent/unregistered-selector `/messages` passthrough transparently proxies its Anthropic wire payload. A scoped audit session has no merchant context-ID, so the router seals its uploads under a tenant pseudonym derived from the audit session identifier — a namespace no merchant tenant can reach.
- **Files API checksum dedup (`file-dedup.ts`) — LIVE.** `dedupUpload(file, resolvedRoute, env)` SHA-256s bytes, scopes optional KV reuse by keyed tenant pseudonym + provider account + file policy + compatible prompt groups + hash, verifies cached upstream objects through the provider-neutral file service, and returns a complete internal provider reference. Dedup records expire within 30 days and never later than upstream expiry; a `discard:` key, one per upload app-ai could not delete, has no expiry and is removed once that delete succeeds. `FILES_KV` holds metadata only, never file bytes, and is never public-reference correctness authority.
- **Every Anthropic upload expires in 30 days.** The `anthropic-provider-files` policy's `requestedLifetimeSeconds` (`model-catalog.ts`) is sent as `expires_in_seconds` on every upload, Anthropic deletes the file at the `expires_at` it answers, and the adapter seals that expiry into the reference and the dedup record. An upload whose answered expiry is missing, unreadable, or shorter than a full reference lifetime is deleted and refused; one that will not delete is kept under its own `discard:` key in `FILES_KV`, with no expiry, until the next upload of the same bytes on the same route deletes it, or, for a Grader session's upload, until the session ends. A Grader session's uploads go sooner than their expiry, when the session ends. Under a policy that requests a lifetime, a dedup hit is reused only while its file has at least a full reference lifetime (15 days) left — a file with less, an expired one, or one with no expiry is uploaded afresh — so every reference runs its whole 15 days and ends before its file. Files uploaded before uploads expired carry no expiry and stay until deleted ([docs/DECISIONS.md #5](docs/DECISIONS.md#5-uploaded-files-expire-and-kv-dedup-reuses-one-only-while-a-full-reference-fits), [docs/KNOWN-ISSUES.md](docs/KNOWN-ISSUES.md)).
- **Image vs document block typing (`chat.ts::buildFileContent`).** Each opaque `fileId` is resolved and route-validated before provider I/O, then typed as `image` (mime `image/*`) or `document` from stored/provider metadata. Images MUST be `image` blocks — Anthropic 400s an image inside a `document` block, which is exactly the placement screenshot.
- **count_tokens pre-flight.** `messages.ts` best-effort logs an estimate (warns past a soft threshold) for large payloads — wrapped in try/catch, NEVER gates/rejects the live request.
- **Opt-in and adaptive output effort (model-gated).** A registry entry MAY carry semantic `effort` or an `adaptiveEffort: { default, escalated }` policy; the two are mutually exclusive. `/messages` maps the content-free `X-Personalizer-QC-Escalated: 1` recovery header onto the escalated value, so the registry — not the caller — owns every effort choice. The request carries only registry effort, and the selected adapter maps or omits it according to the concrete model capability; the Anthropic capability gate lives in `adapters/anthropic-wire.ts`. `onboarding-review-all` runs low by default and medium on bounded recovery; the holistic proposal stays medium; per-page proposal/review stay low. Effort steers thinking but reserves nothing for the answer, so every conductor prompt carries its model's documented maximum output as its `maxTokens` ceiling, resolved from the model the route selects ([docs/DECISIONS.md → Conductor prompts carry their model's maximum output](docs/DECISIONS.md#conductor-prompts-carry-their-models-maximum-output)). The Grader chat is the one prompt whose effort is deployment configuration: `GRADER_CHAT_EFFORT`, sent only when the resolved model reasons, so the registry entry declares none and its group needs no `reasoning` capability.
- **Cascaded onboarding QC.** `onboarding-review-gate-all` classifies every dirty page from bounded whole-store evidence on the `onboarding-qc-gate` group's fast profile with a compact output budget. Only failed, uncertain, malformed, or uncovered pages enter `onboarding-review-all` on the balanced `onboarding-visual` profile for detailed correction generation. The gate group borrows the `onboarding-visual` provider file route, so both passes read one uploaded evidence set.

### The `/chat` agent loop (`handlers/chat.ts` + `src/toolsets/`)

`POST /chat` runs the provider-neutral tool-use agent loop:

```
model → (tool_use?) → execute tool (owning toolset) → tool_result → model → …   (capped at MAX_ITERATIONS = 8)
```

streaming text out as it arrives. Response shape is chosen by `Accept`:

- `Accept: text/event-stream` → SSE protocol (events: `text`, `tool_call`, `tool_result`, `done`, `error`).
- otherwise → a single JSON object identical to the `done` payload.

`X-Personalizer-System-Prompt` selects the prompt (`chat` default, `onboarding`, `placement`, `proposals`, `analytics-insights`). Per-prompt model / max_tokens / whether tools are sent all come from the prompt registry (see below) — not hardcoded in the loop. The frozen cross-repo contract is in the lib repo at `packages/storefront/src/admin/ai/CONTRACTS.md` (§1 SSE protocol, §2 tools, §8 referencing).

**Toolsets (`src/toolsets/` — standards in [docs/TOOLSETS.md](docs/TOOLSETS.md)).** The AI tools are organized into named TOOLSETS, one module directory per backend, each encapsulating its canonical tool definitions, dispatch/executors, normalizers, and degrade conventions. `composeToolsets(subscriberParties, { contextId, env }, availableAiTools, logger)` (`toolsets/registry.ts`) composes the endpoint's tool surface per request. Platform toolsets are data-driven off `AvailableIntegrationParties`; the four Personalizer `/v2/ai-tools/*` definitions require their exact names in `AvailableAiTools` under `AiToolsContractVersion === 1`, while missing or unsupported versions fail closed and `get_entity_context` remains independent. `handleChat` sends only the filtered definitions and routes every `tool_use` through the composition; unadvertised names degrade without a Brain call. Personalizer successes are checked for required PascalCase members, and raw failure bodies are operationally logged but never model-visible. When Brain marks a list read partial with `X-Ls-Has-More-Results: true`, the tool result tells the model plainly that only the first N entries are shown and the store has more. The four platform toolsets — `shopify` (`shopify_rest_request` + `shopify_graphql`), `bigcommerce` (`bigcommerce_rest_request`), `klaviyo` (`klaviyo_rest_request`), `google-ads` (`google_ads_gaql_query`) — are transparent passthroughs to the merchant's platform APIs through Personalizer's integration bridge (`v2/integration-bridge/*`): app-ai never holds a platform token; each is party-gated by its own descriptor's `integrationParties` declaration (the source of truth for that pairing) and resolves only the CALL CHANNEL (context-ID + the `PERSONALIZER_INTEGRATION_BRIDGE_TOKEN` Workers Secret + Personalizer base URL via the `src/config.ts` accessors — `toolsets/integration-bridge.ts`); the proxy URL `{party}` segment is the matched `IntegrationParty` name (`v2/integration-bridge/{party}/…`), and the `X-Ls-Integration-Bridge-Error` response header discriminates the platform speaking (surfaced verbatim as data, any status) from LimeSpot-layer failures (degraded with the envelope's `ExceptionType`). Which subscribers see a platform toolset is decided purely by their available parties — no endpoint allowlist.

**CLIENT-tool mode (LIVE — first consumer `onboarding-chat`).** The loop also carries a client-tool path for a prompt whose tools execute on the CLIENT, not in the worker. When a registry entry carries `clientTools` (`usesTools: false` alongside it — the two are mutually exclusive), `handleChat` sends THOSE tool definitions to the model in place of the server toolset and runs the loop in client-tool mode: on a `tool_use` stop it emits the `tool_call` SSE events, returns the calls to the client in the `done.toolCalls` array (`stopReason: 'tool_use'`), and STOPS the turn — it never executes them and makes no Brain proxy call. The client (the lib) runs each tool (in a browser iframe over the merchant's live store), appends the `tool_result` turn, and calls `/chat` again to continue the loop; a turn that ends with text carries `done.text` and no `toolCalls`. The first live consumer is the **`onboarding-chat`** prompt, which carries **`look_at_page`** (`lib/client-tools.ts` — capture a full-page store screenshot; `page?: string` hint). It composes `chat`'s Studio blocks with its own look-at-page block in place of `chat`'s data-tools fragment (`get_store_analytics` / `get_entity_context` aren't sent in client-tool mode), so Studio's optimizer chats that select it keep the whole Studio chat and can look at a page on demand.

**Referencing (`context.refs`).** `body.context` may carry `refs` — entity references anchoring the conversation to specific entities. `lib/references.ts` owns both the wire shape and the valid type literals: `RECORD_REF_TYPES` (Personalizer-resolved, each needing an `id`) and `ANALYTICS_REF_TYPES` (resolved from the ref's own `metadata`) declared there are the whole vocabulary, and the split between them is what decides whether resolving a ref costs a Personalizer call. The flow:

- **Intake:** array-only; non-object entries, invalid `type` literals, and record-type entries without an `id` string are dropped; capped at `MAX_CHAT_REFS = 5` (first five kept). Requests without refs behave identically to a refs-free build (byte-identical system array — cache safety).
- **Eager Referenced-Entities block:** every surviving ref resolves concurrently (`Promise.allSettled`) — record types via `fetchEntityContext` (`toolsets/personalizer/entity-context.ts`, context-ID forwarded on every Personalizer call, ONE shared subscriber lookup per block build), analytics types from the ref's own `metadata` with NO Personalizer call. A failed resolve degrades that ref's line to `(could not load)`; the block never throws. The block (frozen format: `## Referenced Entities` heading + preamble + one `- [<type>] "<label>" (<anchor>): <payload>` line per ref) is appended by `buildSystem` as a separate, FINAL, **uncached** system block, so the 1h-cached registry prefix and the ≤4 breakpoint budget are untouched.
- **Lazy `get_entity_context` tool** (the personalizer toolset, `toolsets/personalizer/index.ts`, registered with the other tools whenever `entry.usesTools`): the model derefs an entity by `{ type, id }`. Record types → the same `fetchEntityContext` resolution (`{ok:false,...}` degrade on any thrown failure, like the other tools); analytics types → resolved worker-side from the request's refs (`refCategoryPath(ref) === input.id`, fallback first ref of the matching type; `id` here is the category path `analytics/{tab}` / `analytics/{tab}/{metricKey}`) — NO Personalizer call, `{ok:false, result:{error:'analytics reference not attached to this request'}}` when absent. The composition's `execute(name, input, { refs })` receives the surviving refs threaded from `handleChat` → `runAgentLoop`.
- **Record resolution (`toolsets/personalizer/entity-context.ts`):** `fetchEntityContext(type, id, contextId, env)` composes the frozen model-visible `AiToolEntityContext` shape — declared in `toolsets/personalizer/entity-context.ts`, member order and null-member omission pinned by `test/entity-context.test.ts` — from Personalizer's per-record admin endpoints — campaign probes `v2/discount-campaigns/discount-campaign/{guid}` → `v2/html-campaigns/html-campaign/{guid}` → `v1/imageCampaigns?guid=` (Kind = `discount` / `html` / `image`); segment → `v1/subscriberSegment?guid=`; progress-bar → `v2/progress-bar-campaigns/{guid}` (+ the subscriber's CurrencyCode as `Currency`); bundle → the discount route with a bundle-flavored Summary. `v2/accounts/subscriber` is loaded per resolution: its Guid tenant-checks every loaded entity (the discount cache is guid-keyed; the v1 segment load is not tenant-scoped). Discount/bundle `Related` = the targeted segments (per-guid loads, tenant-checked, non-deleted). A miss — 404/204/5xx record fetch, cross-subscriber, deleted — yields `{ Type, Id, Found: false }`; a malformed guid, unknown type, failed subscriber lookup, Personalizer 401/403, or network failure throws (→ the degrade paths above).

Entity-context fetches are NOT cached (no KV) — fresh per call. The `chat` prompt (`src/prompts/chat/`) instructs the model to treat a present Referenced-Entities section as THE topic (never ask "which one?").

### Prompt registry (`prompt-registry.ts` + `src/prompts/`)

`prompt-registry.ts` is a thin registry mapping prompt name → metadata. Its `SystemPromptEntry` interface, in that file, is the source of truth for what an entry may carry and which fields are optional; two exclusivity rules ride it — `clientTools` is mutually exclusive with `usesTools` (see CLIENT-tool mode above), and `adaptiveEffort` is mutually exclusive with `effort` (see Token-saving levers above).

It is the **single source of truth** for each prompt's group, route, token
budget, and tool choices. Both handlers read text + resolved metadata through
`getSystemPrompt(name, env)`. Every entry has exactly one required group, and a
group declares only two things: the capability **tier** it runs on and the
capabilities it **requires**. It names no provider, profile, or file policy.

Routing is `prompt → group → tier → configured model id → model family →
provider`. The tier binds to `MODEL_FAST` / `MODEL_BALANCED` / `MODEL_FRONTIER`
(with sparse per-prompt exceptions in `MODEL_OVERRIDES`), and the model id
itself decides the provider, API family, capabilities, and direct-file policy
through the **model catalog** (`src/inference/model-catalog.ts`). Pointing a
tier at another provider's model is therefore a settings change, not a code
change — the catalog must know the model's family, and the resolved
capabilities must satisfy every group on that tier — a group that converses in plain text
requires `textConversation`, which every chat family has except OpenAI's single-turn one, and the Workers AI visual judge does not
([src/inference/CLAUDE.md](src/inference/CLAUDE.md)). `image-selection` and
`placement` run on the fast tier, the visual/structured groups on balanced, and
the Studio agent/industry groups on frontier.

The registry also owns the typed prompt inventory and every file-reusing
fallback edge. Initialization rejects orphan groups, feature/requirement
mismatches, borrowed routes that are themselves borrowed, and fallback edges
crossing file routes; resolving a route additionally rejects a model whose
capabilities miss the group's requirements, a file policy incompatible with the
resolved API family, and a per-prompt override that would move one prompt off
its group's shared provider file route. The exact map is in
[docs/PROMPT-GROUPS.md](docs/PROMPT-GROUPS.md) and frozen
by `test/prompt-groups.test.ts`. Canonical provider-neutral inference and opaque
file contracts live in `lib/inference-types.ts`. Public uploads use repeated
`prompt` multipart fields and every success returns one shape — `{ id, type }`
plus a prompt-addressable `references` map naming every declared prompt, whose
values remain opaque. Prompts sharing a route share the reference minted for it,
so a single-route upload names them all against that one value.

All prompt text lives ONLY under `src/prompts/`. The barrel imports each `.md`,
re-exports every prompt's final text, and each composed prompt assembles its
ordered fragments with `composePrompt`.

**Unified single / multi-file / COMPOSED / shared-text convention.** A registered prompt is one of four shapes; every public selector resolves to its registry entry:

- **Simple** → one file: `src/prompts/<name>.md` (e.g. `placement.md`). Import it and use it as `prompt`.
- **Multi-file** → a folder: `src/prompts/<name>/` (e.g. `image-selection/`), made of parts:
  - `prompt.md` — the main system prompt (re-exported by the barrel).
  - a sample/attachment file (e.g. `sample.md`) — NOT part of the system prompt; re-exported by the barrel and wired as an `attachments` entry `{ content, mimeType, filename }` so `messages.ts` uploads it (Files-API dedup + extended cache) and prepends it to the first message as a document block. Attachments are image-selection-only today.
- **Composed** → a folder of `_`-prefixed BLOCK files, no `prompt.md`, PLUS its own `index.ts` that assembles the system text with `composePrompt(...)` (the helper lives in `src/prompts/_compose.ts`) from an ORDERED mix of per-prompt fragment files in the prompt's own folder (`_intro.md`, `_receive.md`, …) plus SHARED blocks under `src/prompts/onboarding-shared/` (`_shared-*.md` / `_block-*.md` — box vocabulary, the JSON-only hardening lines, the mobile rule, the correction verbs, …) so every composing prompt shares that instruction (edit a block once → all of them update). The composed prompts are the onboarding propose/review pairs (`onboarding-batch` / `-all`, `onboarding-review` / `-all`), the cart-drawer conductors (`cartdrawer-batch-all`, `cartdrawer-review-all`), `optimize-demand`, and the Optimization conductor's four steps, which compose its shared blocks in `src/prompts/optimization-shared/` after the agents master rules, plus the four conversational prompts `chat`, its look-at-page twin `onboarding-chat`, `billing-assistant` and `grader-chat`, each around its own identity — Studio's names its platforms, the Grader's names none and leaves platforms to the booklet — (all four byte-pinned by `test/assistant-prompt-blocks.test.ts`): `chat`, `onboarding-chat` and `billing-assistant` compose the agents master rules in `src/prompts/assistant-shared/` right after their identity — a core copied byte for byte from `limespot/root`'s `_standards/agent-rules-core.md`, which Brain's merchant agents carry too, and held to that file by `test/shared-agents-core.test.ts`, then the rules that hold in a conversation with the owner — and `chat` and `onboarding-chat` also compose the shared Markdown chat-formatting block and the Studio blocks, while `grader-chat`, whose replies lib shows as plain text, composes its one boundaries block, its Growth Agents team block, its own plain-text formatting block, its buttons block — the one `choices` envelope a reply may end with, which the link guard finds as lib does and holds to that one shape before it reads the decoded prose, labels and links — and the marketing booklet `GRADER_CHAT_BOOKLET_VERSION` selects; which folders are prompts vs shared blocks, and why the `-all` twins are not duplicates, is in [src/prompts/CLAUDE.md](src/prompts/CLAUDE.md). Here a `_`-prefixed `.md` is a BLOCK PART that IS explicitly imported + composed — it just isn't a standalone `<name>` you select via the header. The composed text is pinned byte-for-byte by the byte-equivalence gate (`test/onboarding-prompt-blocks.test.ts`) and its STABLE ORDER is the cacheable system prefix (the `cache_control` 1h breakpoint in `messages.ts`; per-shop screenshots + manifest ride AFTER it — "variable data last"). Per-prompt design/maintenance docs live at `docs/prompts/<name>.md` (process: [docs/PROMPT-AUTHORING.md](docs/PROMPT-AUTHORING.md)).
- **Shared-text alias** → an explicit named barrel export reuses another registered prompt's final text when both names have the same semantic contract but intentionally different routing or access. `visual-verify-free` is the only alias; it owns a distinct registry entry and maintenance doc, and a shared-text edit updates both docs.

Adapter-internal mediation prompts also live under `src/prompts/`, but they have
no public selector, registry route, or per-prompt maintenance page. Their owning
adapter defines the bounded call contract, and `src/prompts/CLAUDE.md` inventories
them separately from registered prompts. `kimi-html-retrieval` is the current
internal prompt.

`image-selection` is the multi-file prompt with an attachment (system text `prompt.md` + the `sample.md` attachment); the composed prompts are the onboarding + cart-drawer + optimize set. Design docs: [docs/prompts/image-selection.md](docs/prompts/image-selection.md), [docs/prompts/onboarding-batch.md](docs/prompts/onboarding-batch.md), [docs/prompts/onboarding-review.md](docs/prompts/onboarding-review.md).

The whole-store proposal owns the initial currency decision. Deterministic currency validation and the
registered `onboarding-currency-recovery` one-shot form a targeted hard gate before common QC.
If the initial proposal omits a valid verdict, the recovery prompt
reuses at most four already-uploaded price tiles and returns exactly one candidate selection or strictly
validated six-argument format before the first QC render. It is a bounded omission recovery, not a
post-QC currency island. Advanced CSS enters the registered `onboarding-css-review` specialist only
when common QC emits `advanced-css-required`; ordinary review-all responses cannot return visual
actions. The currency recovery maintenance contract is
[docs/prompts/onboarding-currency-recovery.md](docs/prompts/onboarding-currency-recovery.md).

`prompt-registry.ts` is the authoritative list of registered prompts. The reading aid over it — every prompt with its shape, endpoint, tools, and role — is [docs/ARCHITECTURE-MAP.md](docs/ARCHITECTURE-MAP.md) → "Registered prompts", read on demand; the doc-sync rule that keeps the two in step is [src/prompts/CLAUDE.md](src/prompts/CLAUDE.md). No third, partial copy lives anywhere.

### Website-Analysis probes (`probe-<id>`)

A **probe** is a header-selected `POST /messages` system prompt for Website Analysis: it takes storefront evidence (cleaned-HTML documents + screenshot images, uploaded via `POST /files` and referenced as content blocks on the first user message — the same muscle as `image-selection`) and returns **JSON ONLY** per a fixed schema (no tools, no prose). `/messages` needs no per-probe change — it serves any `X-Personalizer-System-Prompt`-selected prompt. The convention lives in `prompt-registry.ts`: every probe registers under a `probe-<id>` name (`PROBE_PREFIX = 'probe-'`, `isProbeName()`), ships its system text at `src/prompts/probe-<id>/prompt.md`, records its frozen output contract in the `PROBE_SCHEMAS` index, and has a maintenance doc at `docs/prompts/probe-<id>.md`. A new probe drops in identically — a new prompt file + registry entry + `PROBE_SCHEMAS` entry + maintenance doc, no handler edit. Which probes exist and what each returns is `PROBE_SCHEMAS` in `prompt-registry.ts`, cross-checked against the registry by `test/probes.test.ts`; the inventory table in [src/prompts/CLAUDE.md](src/prompts/CLAUDE.md) names them with their roles, and each has its own maintenance doc under `docs/prompts/`. Every probe shares one call shape: `POST {base}/messages` with `X-Personalizer-System-Prompt: probe-<id>`, a standard Anthropic messages payload whose first user content is the uploaded evidence blocks, and an assistant text body that parses as that probe's frozen schema.

**Bundler text rule (no runtime fs):** `import x from './prompts/placement.md'` — and nested multi-file imports like `import x from './prompts/image-selection/prompt.md'` — resolve to the file's string contents at BUILD time, in both targets with the SAME import specifier (no `?raw`):

- **Worker** — `[[rules]] type = "Text"` (`globs = ["**/*.md"]`) in `wrangler.toml` makes esbuild emit each `.md` as a text module. The `**/*.md` glob matches nested folders, so multi-file prompts bundle without any config change.
- **Tests** — an inline Vite plugin in `vitest.config.ts` does the same for any `.md` at any depth (`transform` turns `.md` into `export default "<contents>"`).

To add/edit a registered prompt: create/edit the `.md` file(s) under `src/prompts/` (a single `.md` for a simple prompt, or a `<name>/` folder for a multi-file prompt), add/update its registry entry in `prompt-registry.ts`. If a prompt needs runtime `${}` interpolation it can't be a static `.md` — keep that dynamic bit in JS.

> There is only ONE prompt location: `src/prompts/`. Simple registered prompts are a single `.md`; advanced/multi-file prompts are a folder (`prompt.md` + a `sample`/attachment file). Registered prompts have maintenance docs under `docs/prompts/`; adapter-internal mediation prompts are documented with their owner in `src/prompts/CLAUDE.md`. No stray second prompts directory exists anywhere in the repo.

### Logging

Latency-critical visual `/messages` prompts (onboarding proposal/review, currency recovery,
cart-drawer, optimize, and visual verification) proceed directly to inference instead of awaiting the
advisory `count_tokens` diagnostic. Other large payloads may still use that best-effort estimate; it
never gates correctness.

Application code logs only through the request-scoped `LoggingRuntime` in `lib/logger.ts`. Each
`LOG_TARGETS_<LEVEL>` binding routes that level to `ignore`, `console`, `seq`, or a comma-separated
fan-out; environment names carry no policy. Production routes `error`/`fatal` to private Seq and all
other levels to `ignore`, with Cloudflare application console output disabled. Local configuration
routes every level to both console and Seq. Seq delivery uses `waitUntil`, is fail-open, and accepts
an optional `LOG_SEQ_API_KEY`; the configured shared endpoint supports anonymous CLEF ingestion.

`/messages` and `/chat` emit correlated TRACE records for complete model-visible input, assistant

## Local AI dev — provider-neutral Claude Code/Codex fulfillers

Local dev fulfils inference through the local Anthropic-compatible shim, not a paid provider API. Claude Code is the standard default and uses the machine's Claude Code authentication.

The same shim exposes a provider-neutral local fulfiller selection. The default
`LOCAL_AI_FULFILLER=claude-code` preserves streaming and the server/client tool
bridge. `LOCAL_AI_FULFILLER=codex` requires explicit `CODEX_LOCAL_MODEL` and is
limited to one-shot tool-free visual/structured requests, streamed or not. It invokes `codex exec`
with `--ephemeral`, a read-only sandbox, image files, an output schema, JSONL
events, cancellation, zero-byte inherited AGENTS/project instructions, ignored user configuration/rules, disabled shell/web/plugin/
subagent/app-connector/dependency-install tools, ChatGPT-only saved authentication by default, and a secret-minimized child
environment. `CODEX_API_KEY` requires `AI_CHANNEL=prod`; tool-loop requests fail
closed.

**How it works.** The Anthropic adapter talks through exactly one wire seam — `src/inference/adapters/anthropic-wire.ts`, where `ANTHROPIC_API_BASE` is read via `anthropicApiBase(env)`. So the whole toggle is one line in `.dev.vars`:

```
ANTHROPIC_API_BASE=http://127.0.0.1:8788
```

`scripts/dev-claude-shim.mjs` (started by `npm run dev:shim`) is a local Anthropic-API-compatible HTTP server on `:8788`. Its canonical one-shot fulfiller dispatches to either the `@anthropic-ai/claude-agent-sdk` `query()` path or bounded `codex exec`; streaming/tool requests remain Claude-Code-only. No `src/` route change and no `[env.dev]` block are needed: plain `wrangler dev` reads `.dev.vars`, which overrides the production provider origin. Production is unchanged.

**Run it (two terminals, or shim in the background):**

```
npm run dev:shim     # terminal 1 — free local shim on :8788
npm run dev          # terminal 2 — wrangler dev on :8787, ANTHROPIC_API_BASE → the shim
```

**The FREE-stack worker MUST be started via `npm run dev` (the `scripts/dev.mjs` launcher).** It stamps the served worker with `--define __APP_AI_REV__:"<short HEAD>"`, so `/health` reports the exact rev as `buildRev`. The lib's FREE-stack preflight (`preflightMatrixStack` in `tests/e2e-playwright/studio-ai/fixtures/harness-boot.ts`) always rejects a `'dev'` / absent `buildRev`, AND — under `LS_EXACT_STACK` (the fork-matrix evidence run) — the exact-revision compare fires by default (GAP-A): it compares the served `buildRev` against an EXPECTED rev that **DEFAULTS to the sibling `../app-ai` checkout's frozen HEAD** (`git -C ../app-ai rev-parse --short HEAD`) when `LS_APP_AI_EXPECTED_REV` is unset, so a stale worker at a real short-sha FAILS CLOSED instead of passing green (the env pin overrides the default; `LS_APP_AI_REPO_PATH` points elsewhere; an unresolvable checkout is a hard stop in exact-stack mode). The auto-resolve default is GATED on `LS_EXACT_STACK` — symmetric with the lib asset-hash pin — so a NON-exact-stack caller that doesn't pin the rev stays lenient (a worker legitimately serving an earlier commit than a since-pulled `../app-ai` HEAD is not spuriously rejected). A stale worker would exercise code other than the reviewed checkpoint. See `preflight-fail-closed.spec.ts`. A bare Wrangler launch bypasses the repository stamp and is NOT valid evidence; a define-less production `/health` fails with 503. Before any evidence run, verify the served rev matches HEAD:

```
test "$(curl -s 127.0.0.1:8787/health | jq -r .buildRev)" = "$(git rev-parse --short HEAD)"
```

If it differs, the worker was launched without the define — restart it via `npm run dev`. Production and preview deploys use `npm run deploy` / `npm run deploy:preview`; both stamp the exact checked-out revision and refuse to run when Git cannot resolve it.

**What the shim implements** (exactly the surface the worker calls):

- `POST /v1/messages` one-shot — a non-stream request (the unregistered passthrough) or a tool-free `stream:true` request (every registered prompt, probes and proposals included). Accepts content blocks incl. `image` + `document` (`source:{type:'file',file_id}`) + a `system` array; fulfils it through the selected one-shot fulfiller (Claude Code or Codex); returns one Anthropic body `{ content:[{type:'text',text}], usage, stop_reason }`, or that same message as the Messages API event sequence when the request streamed. A wrapping `code fence` is stripped so JSON-only probes/proposals parse cleanly.
- `POST /v1/messages` `stream:true` with tools — the `/chat` tool loop. Maps the SDK's assistant text to `text_delta` frames and synthesizes the full Anthropic envelope (`message_start` / `content_block_start` / `content_block_delta` / `content_block_stop` / `message_delta{stop_reason}` / `message_stop`) that `src/inference/adapters/anthropic.ts` parses.
- `POST /v1/files`, `GET /v1/files/{id}`, `DELETE /v1/files/{id}` — an in-memory temp store keyed by a generated `file_id`, remembering mime (image vs document) and answering the `expires_at` an upload's `expires_in_seconds` asked for; rehydrated into the `query()` user turn as inline base64 at message time.
- `POST /v1/messages/count_tokens` — `{ input_tokens }` (char/4 estimate; advisory).
- **Tool-use bridge** for the `/chat` tool loop: each personalizer tool (`get_store_analytics` / `list_segments` / `list_campaigns` / `get_store_config`) is registered as an in-process `createSdkMcpServer()` tool whose handler makes the SAME Personalizer `v2/ai-tools/*` call the worker's personalizer toolset makes. The SDK resolves the loop; the shim emits the equivalent `tool_use` frames (bare tool name, harness built-ins filtered out). Enable it by setting `LS_DEV_CONTEXT_ID` (a dev store's context-ID) — the worker's Anthropic seam does not forward the context-ID to Anthropic, so the shim needs it out of band. Without it, tool flows run tool-free (fall back to the real API only if you deliberately switch channels).

**Record/replay response cache (ON by default).** Claude Code fulfilment is free but slow, so a repeated identical call replays from disk instead of re-running the model. `SHIM_CACHE` is an opt-OUT: `SHIM_CACHE=0` (also `false`/`no`/`off`) fulfils everything fresh, and anything else, including unset, leaves recording and replay on. `scripts/dev-shim-cache.mjs` owns the key derivation and the on-disk entries; `scripts/dev-claude-shim.mjs` owns the request-lifecycle wiring, the HIT/MISS/RECORD logging, and the two channels below. BOTH transports are cached: a non-stream response replays as the same JSON body, and a stream replays as the same SSE frame SEQUENCE — recorded frame by frame and re-emitted through the same serializer, never one concatenated blob. Only successful fulfilments are recorded; an error body or error frame never becomes a permanent answer.

**Being on by default is paid for by being loud.** A recorded answer is byte-for-byte the fresh one, so a caller who does not know the cache exists could not otherwise tell them apart — and the shim's own log does not help, because the shim is a separate background process and whoever commanded a run is reading a different terminal. So the shim answers the question over the wire, two ways: every `/v1/messages` response carries **`x-dev-shim-cache: hit | miss | off`**, and **`GET /health`** returns `cache: { enabled, directory, attachmentIdentity, hits, misses, recorded, recordFailures }`. The counts are per PROCESS and never reset, so a test harness reads `/health` before and after a run and subtracts to report how many of that run's model calls came off disk. Every call still logs `cache HIT` / `cache MISS` / `cache RECORD` too.

The key is a SHA-256 over the canonical (key-sorted) JSON of the transport, the effective model, the context-ID, the attachment rule, and the request body. The body is NORMALIZED first, and the two kinds of normalization are deliberately different. An ATTACHMENT (`file` source's `file_id`, inline `base64` `data`) is replaced by its POSITION among the attachments of its kind — `<shim-cache:file:N>`, N counting in document order, never derived from the id itself. A TOOL id (`tool_use.id` / `tool_result.tool_use_id`) is replaced from one shared id→ordinal map, so which result answers which call still keys. Position for attachments is not a simplification, it is the correctness requirement: the shim mints a new `file_dev_…` per upload, but the worker also DEDUPES uploads by content, so two page tiles that happen to render byte-identically arrive as one id used twice and as two ids on the next run. Numbering by identity therefore shifted every later ordinal whenever a duplicate appeared or stopped appearing, which is what kept the onboarding whole-store call from ever matching its own recording. Everything else, prompt text and tool-result CONTENT included, is hashed verbatim, and matching is exact: no approximate match, no "closest entry". The limitation that follows is deliberate and must stay explicit — an attachment contributes its position and its source kind and nothing else, so two calls differing ONLY in the attached image, or only in whether two of those images were one deduped upload, share a key and share the answer. A test that varies the image on purpose runs with `SHIM_CACHE_ATTACHMENT_BYTES=1`, which keys attachments by a SHA-256 of their bytes instead.

Entries are one `<sha256>.json` per call under `SHIM_CACHE_DIR` (default `.dev-cache/claude-shim/`, gitignored — a recorded payload can carry store data and is never committed). Each entry is self-describing (`cacheFormat`, `key`, `transport`, `model`, `contextId`, `attachmentIdentity`, `recordedAt`, an advisory `label`, and the `response` or `frames`), and a `cacheFormat` bump makes every older entry read as unusable rather than replay under stale rules. Delete the directory, or start the shim with `SHIM_CACHE_RESET=1`, to invalidate everything.

**Using a real paid provider API from local (rarely — prod-only by policy)** requires `AI_CHANNEL=prod`. Worker config accessors fail closed for every non-loopback Anthropic, OpenAI, Moonshot, Kimi Code, and Gemini origin outside production without that opt-in, and in production each accepts only its provider's own API base, written exactly. The shim applies the same Anthropic startup guard and rejects a selected Codex API-key credential without the opt-in. The Codex child receives only an allowlisted runtime/auth environment, never app/provider secrets. `scripts/dev-claude-shim.mjs` and `scripts/dev-local-fulfillers.mjs` are dev-only — never bundled or run in production.

## Hard rules

- **The live surface is a coordinated external contract with a fixed deployment order.** `/messages`, context validation, CORS, and cache behavior remain stable. The `/messages` keep-alive answer is opt-in by a body field, so it deploys ahead of the lib that requests it and leaves every request without it unchanged; its rollback runs the other way, the lib sender rolled back or its opt-in removed before this worker, because a worker without the mode refuses the member on the strict Grader chat body and forwards it to the provider on the unregistered passthrough ([docs/DECISIONS.md #36](docs/DECISIONS.md#36-a-long-messages-call-can-keep-its-connection-alive-by-the-callers-choice)). Usage reporting deploys Brain first: Brain's `POST v2/agents/report-chat-usage` is live before a worker that reports to it, because a report is never retried and one the route does not answer drops that response from the store's AI cap for good; its rollback runs the other way, this worker's sender rolled back before the Brain endpoint is. The Studio chat's `clientActions` gate deploys before the lib that lists those actions, and while any lib in service may omit the field, a worker rollback keeps the gate or goes behind the prompts that teach `requestSupport` and `moveBox`, never to a worker that teaches either unconditionally, because a lib without their handlers ignores both directives ([docs/DECISIONS.md #43](docs/DECISIONS.md#43-studio-chat-offers-support-and-movebox-only-to-a-client-that-says-it-carries-them-out)). The `/files` upload body is versioned in place: every caller sends repeated registered `prompt` parts, and app-ai returns the frozen opaque response — one reference plus the `references` map naming every declared prompt. The app-ai and lib sides of that contract are tested together and deployed worker-first: `TOKEN_ENCRYPTION_SECRET` exists on the worker before the worker deploys (an upload without it fails closed before provider I/O), then the worker deploys, then Studio. A worker rollback is paired with a Studio rollback: Studio caches the `file_ref_v1_…` references it receives ([docs/KNOWN-ISSUES.md](docs/KNOWN-ISSUES.md) → reference lifetimes), and a rolled-back worker forwards such an id to Anthropic as a raw file id, which Anthropic rejects. `FILES_KV` dedup keys are namespaced by tenant pseudonym, provider account, file policy, compatible groups, and media type, so a rolled-back worker reading its bare-hash key misses and re-uploads rather than reading a record it cannot interpret. A worker rolled back past upload expiry uploads without an expiry again and reuses a dedup record whatever its file has left, so a reference it mints can outlive its file by up to 15 days and fail once the file expires, and its uploads carry no expiry again. Deletion of a Grader session's uploads and of the audit's record deploys before limespot.com's privacy copy promises it, and a rollback below it is paired with a rollback of that copy ([docs/AUDIT-AUTH.md → Retention](docs/AUDIT-AUTH.md#retention)). The 30-day session and both Grader kill switches deploy before the extension and lib: their response fields are additive. The rule holding a build naming no build time to its plan version deploys before an extension build that may omit `X-LimeSpot-Extension-Built-At`, and a worker rolled back below it reads such a build as made at `2026-10-03T00:00:00Z`, so while one serves, `GRADER_EXTENSION_BUILT_AFTER` stays at or before that instant ([docs/AUDIT-AUTH.md → Kill switches](docs/AUDIT-AUTH.md#kill-switches)). The audit session record keeps the whole-session totals a worker without runs enforces its limits from, and each run's upload count the first worker with runs enforces its per-run ceiling from, so a rolled-back worker still holds live grader sessions to them ([docs/AUDIT-AUTH.md](docs/AUDIT-AUTH.md) → Durable Object deployment).
- **The AI provider allow-list mirrors the DPA's AI sub-processor list; a provider is added to the root `ai-providers.json` first, then to the website DPA, and the Privacy Policy where its retention or training terms differ, then to this list, and no customer-content route selects it before that DPA is live.** `AI_SUBPROCESSORS` in `src/lib/ai-providers.ts` is that list, `test/ai-providers.test.ts` pins it to the workspace's canonical `ai-providers.json` in `limespot/root` — the same DPA names and API origins, with only Moonshot and Kimi Code unlisted — the published-DPA step of CI's `test` job holds that same file to the DPA as published, failing until the live page's sub-processor list prints every `dpaName` exactly, so a provider added to the file stays red here until the website DPA naming it is merged, and the account confirmations it also rests on are recorded in [docs/AI-PROVIDERS.md](docs/AI-PROVIDERS.md).
- **Brain is the source of truth** for the `/v2/ai-tools/*` request/response shapes (`toolsets/personalizer/index.ts`), the per-record admin endpoints consumed by `toolsets/personalizer/entity-context.ts` (`Controllers/V2/DiscountCampaignsController.cs`, `Controllers/V2/HtmlCampaignsController.cs`, `Controllers/V1/ImageCampaignsController.cs`, `Controllers/V1/SubscriberSegmentController.cs`, `Controllers/V2/ProgressBarCampaignsController.cs`, `Controllers/V2/AccountsController.cs` → `subscriber`), and the `/v2/administrator-authentication/validate-context-id` shape (`auth.ts`). Mirror Brain's C# exactly — verify routes, query params, and fields against the sibling `brain` repo (`Controllers/V2/AiToolsController.cs` `[Route("v2/ai-tools")]` → `store-analytics` / `segments` / `campaigns` / `store-config`; `AdministratorAuthenticationController.cs` → `validate-context-id`). Brain serializes PascalCase with enums as strings and null members omitted (`NullValueHandling.Ignore`) — `entity-context.ts` mirrors that omission. Brain also owns the AI integration-bridge wire contract consumed by `toolsets/integration-bridge.ts` (`v2/integration-bridge/{platform}/rest/{path}` + `/graphql` + `/gaql` routes, the `{ Query, Variables }` / `{ Query, PageSize }` request models, the `X-Personalizer-Integration-Bridge-Token` caller header, and the `X-Ls-Integration-Bridge-Error` discrimination header). Never invent, narrow, or rename a field in `toolsets/` / `auth.ts`; never assume the shape from the sibling app TS, which can be stale.
- **app-ai serves the Studio UX; data agents live in Brain.** A data agent builds its inputs from store data (catalog, orders, picks, analytics), calls the model and stores the result (Upsell & Cross-sell, SEO, Google Ads), and its prompts and logic live in Brain, never here: Brain's runner builds its prompt from the agent's own rows, so a playbook written here has nothing to call it. The Studio chat, conductors and Grader chat stay here: app-ai holds no platform credential, and the Studio chat reaches store data only through Brain's tool routes and integration bridge (`src/toolsets/`) (`../_standards/architecture.md`, "Where an agent lives").
- **One error shape — Brain's wire format — status mapped from the failure.** Every error response is structurally identical to a Brain error (`{ "Message": ..., "ExceptionType": ..., "MessageDetail": ... }`, flat PascalCase, `MessageDetail` omitted when absent), built by `errorResponse`/`errorPayload` in `lib/responses.ts`, so clients keep ONE error parser for both backends. SSE `error` events carry the same payload. Status + `ExceptionType` mirror Brain's mappings: missing context-ID → 401 `MissingContextIDException`; a Personalizer rejection of the validate call relays Personalizer's status + body UNCHANGED; client input validation → 400 `ArgumentException`; unknown route → 404 `RecordNotFoundException`; non-ok provider responses preserve their status and provider exception type (`AnthropicApiException` with raw `MessageDetail`, or `CloudflareWorkersAiException` with its provider code retained in diagnostics); a model call the upstream inference deadline ends, or a Grader chat reply that lands after its message's lease was released, → 504 `InferenceTimeoutException` with `MessageDetail` `inference_timeout`; a registered `/messages` reply stopped at `max_tokens` → 502 `InferenceTruncatedException`; a refused Grader chat message → the status and `ExceptionType` `graderChatRefusal` (`lib/grader-chat-quota.ts`) maps its `MessageDetail` code to (`grader_chat_disabled` 503, `grader_chat_not_in_plan` and `grader_chat_history_unverified` 403, `grader_chat_input_too_long` and `grader_chat_message_reused` 400, `grader_chat_busy` / `grader_chat_not_open` / `grader_chat_run_failed` 409, the four `grader_chat_*_limit` codes 429, `audit_session_expired` 401, `grader_run_revoked` 410 `GraderRunRevokedException`); a production request before the provider configuration validates → 503 `ServiceUnavailableException`, status only, as `/health` answers; a route resolving to a provider that may not serve it in production → 503 `ProviderNotAllowedException` with `MessageDetail` `provider_not_allowed`; an exchange or audit call from an extension build naming a build time older than `GRADER_EXTENSION_BUILT_AFTER` → 409 `ExtensionUpdateRequiredException` with `MessageDetail` `extension_update_required`; an audit exchange, status read, upload or inference naming an unsupported `X-LimeSpot-Audit-Plan-Version`, or naming none from a build naming no build time → 409 `AuditPlanVersionException` with `MessageDetail` `audit_plan_version_unsupported`; an audit exchange of a consumed activation whose session has landed, been superseded, or is bound to another store → 409 `AuditActivationConsumedException` with `MessageDetail` `audit_activation_consumed`; an audit reservation while the session record is past its 1 MB budget → 503 `AuditSessionBacklogException`; invalid provider output becomes that provider's 500 exception; everything else → 500 `Exception` via the router's `errorResponseFrom` catch. Handlers do not invent per-route error envelopes. A keep-alive `/messages` answer carries that same status and envelope inside its body as `status` and `error` (DECISIONS #36). See [docs/DECISIONS.md](docs/DECISIONS.md) #7.
- Prompt `.md` text must match the intended prompt byte-for-byte.
- No new production npm dependencies (the worker bundle stays dependency-free); dev tooling only when a gate needs it.
- **No Hardcoded Config Values** (Tech / Constraints above) — URLs and deploy-time tunables live in wrangler `[vars]` / `.dev.vars` behind `src/config.ts`; missing config throws; no inline fallbacks. Fitness-tested.
- **`main` is read-only to every agent, and a push to it IS a production deploy.** Cloudflare's GitHub integration deploys `main` on push, so that one action carries both the push approval and the deploy approval, named separately, and only an operator performs it. An agent prepares work on a feature branch and never commits on, merges into, pushes to, force-pushes, resets, rebases onto, or enables a pull-request merge targeting `main` (`../_standards/git-and-approval.md`). Committing locally on a feature branch is its own separate approval.
- **Access to the running worker is read-only.** `wrangler tail`, `/health`, and the deployed diagnostics are for inspection; an agent never runs `npm run deploy`, `wrangler deploy`, a secret write, or any other command that mutates the live worker, its bindings, or its secrets. Those flow from a committed change an operator deploys.
- **No AI-attribution in commit messages.** A commit message contains NO `Co-Authored-By: Claude …` / `Claude-Session:` trailer, no "Generated with …" line, and no mention of Claude / Anthropic / any AI assistant as an author or contributor — the subject + body describe the change, nothing else.
