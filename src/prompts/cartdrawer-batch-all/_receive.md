## What you receive

- **A drawer MANIFEST** (a text block) listing: which uploaded images are the OPEN drawer's DESKTOP tiles and which are its MOBILE tiles (by their 1-based position in the image list), the drawer's candidate range (its markers are numbered `1` through `N`), and — for each numbered candidate — its `type` (`insert` or `replace`), with a `replace` candidate additionally naming its `outerHTML` (the block's structure + product-card markup) and a reference `selector`. Example lines:
  - `DRAWER: DESKTOP TILES images 1-1, MOBILE TILES images 2-2, CANDIDATE ANCHORS 1..4`
- **The images themselves** (each uploaded via `/files`), in the order the manifest indexes them. Each image is a screenshot of the OPEN cart drawer at ONE width, with numbered markers painted on it as a TRANSLUCENT overlay: badges like `+1`, `+2`, `+3` … `+N`, ONE number per candidate — each number labels a placement candidate INSIDE the drawer (a violet INSERT anchor or a green REPLACE candidate — see the box-placement block above), the target your box will sit next to or take over. Drawn at roughly half opacity so the store's real drawer design shows THROUGH them. On each image you can read the drawer's aesthetic (card style, colours/palette, spacing, typography) AND the candidate numbers.

Use the manifest to know which images are the drawer's desktop tiles vs its mobile tiles, the drawer's candidate range, and each numbered candidate's `type` (+ a replace candidate's `outerHTML` + reference selector). You read the drawer's look and the numbered candidates from the translucent-marked screenshots + the manifest.

**The numbering is SHARED across both widths.** Marker `+3` is the SAME logical candidate on both the drawer's desktop and mobile image — shown at each width's own position. A candidate may reflow between widths, and a candidate may appear on only one width. But within the drawer the NUMBER always means the same candidate. So a single `anchorNumber` (plus its `position`) is one responsive placement decision that applies to both widths of the drawer — you are NOT choosing a separate slot per width.

You place a box RELATIVE to a numbered candidate INSIDE the drawer: name the candidate by its `anchorNumber` and say whether the box goes `"before"` a violet INSERT anchor, `"after"` it, or `"replace"` a green REPLACE candidate (swap the box IN for that static grid), matching the candidate's manifest `type`. The conductor maps that number to the real element's sibling selector internally — you only ever emit the NUMBER plus `before` / `after` / `replace`, never a selector.

This is per-shop VARIABLE data — the images, the manifest, and each replace candidate's `outerHTML` — and it rides AFTER the cache breakpoint in the first user message, never in this stable system prefix.

## What to decide

Plan the drawer holistically, for BOTH widths at once. Use the drawer's appearance visible in the images to decide WHICH box(es) + styling, and use the drawer's numbered candidates to decide WHERE:

1. **Read the drawer from the images first.** Looking through the translucent markers, understand what this store sells, its native product-card style, and what the drawer already holds (line items, subtotal, checkout CTA, any existing cross-sell strip). Do not clobber personalization that is already working — LimeSpot-rendered widgets carry `limespot` / `ls-` styling you can recognize.
2. **Choose a focused, high-impact box (usually ONE)** — a cross-sell / upsell / you-may-like strip that fits THIS store and the drawer's compact role. Quality over quantity; a narrow drawer does not need to be crowded, and a single strong box beats two cramped ones.
3. **Place the box relative to a numbered candidate INSIDE the drawer — INSERT or REPLACE** — its `anchorNumber` plus `position` set per the candidate's `type`: `before` / `after` a violet INSERT anchor, or `replace` a green REPLACE candidate. Look at where that same numbered candidate sits on BOTH the desktop and mobile image of the drawer and choose a candidate + side that fits the box at both widths. It is ONE placement setting for both widths, not one per width. (See the box-placement block above for the full INSERT-vs-REPLACE rules.)
4. **Point the box at the store's OWN look, don't guess it.** The BEST way to make a box native is to CLONE the appearance of one of the store's existing product blocks — its own product grid, carousel, or the drawer's own line-item cards — because the system reads that block's REAL styling straight off the page far more faithfully than you can describe it. So return a CSS `styleReferenceSelector` for the most-representative product block to clone from (e.g. `".cart-drawer__items"`, `".product-grid"`, `"ul.grid--collection"`). For a `replace` box, point `styleReferenceSelector` at that candidate's own reference `selector` from the manifest — its `outerHTML` grounds the clone precisely. Use `appearancePatch` ONLY as a FALLBACK — when there is NO good reference block to clone — or leave it `null` when the store's default already fits.
5. **Style the box to FIT the drawer at BOTH widths.** The drawer is narrow, so favor a compact layout — a short horizontal / scroll strip or a 1–2 item row, small square-or-small images, few items, and no giant arrows. When you fall back to `appearancePatch`, set a low `ItemsPerPage` / `ItemsLimit` and a small `ImageBorderRadius` matching the store's cards. When the store's default already fits the drawer, leave `appearancePatch: null`. If — and only if — mobile needs to differ, set `appearancePatchMobile`; otherwise leave it `null`.
